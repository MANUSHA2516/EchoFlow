     ECHO Unit Queue-Management System
     Administrator Web Portal — Screen-by-Screen UI Documentation

Prepared from the submitted mockup image, cross-checked against the Research Proposal
                                (Chapters 1, 3 and 5)



1. Introduction
This document reviews the interface mockups supplied for the ECHO Unit queue-management
system and matches each screen to the correct actor (Patient, Staff, or Administrator), a description
of its purpose, and its concrete functions. The mockup image contains twelve distinct screens/states.
Ten of these are clearly Administrator-side screens, consistent with the sidebar navigation labelled
"ECHO Unit Admin" and the Super Admin account shown in the footer of most screens. However,
two of the twelve screens are not admin-specific — they are the system's shared entry points used
by all three actor types (Patient, Staff, and Administrator). These are flagged explicitly below so the
documentation accurately reflects what was actually designed, rather than assuming every screen in
the strip belongs to the admin portal.

The Research Proposal (Section 1.5, Scope of the Study) states that the Administrator Web Portal
consists of eight core screens: a Today's Unit Overview dashboard, a Room/Station Management
grid, a Staff Accounts table, an Add-Staff-Member modal, an Audit Log, a Settings screen, a Register
Station modal, and an Add Echo Room modal. The mockups largely match this list, but the
implementation actually contains a few additional screens/states (an Admin sign-in screen, an
Admin "My Profile" account screen with an edit-profile sub-view, a quick "Add Technician" modal,
and a detailed staff "Access & Role" modal) that are not named individually in the proposal text.
These additions and the minor naming differences are called out under "Notes / Corrections" in the
relevant sections.

Screen 1: Admin Sign-In
 Primary Actor                   Administrator




                        Split-panel sign-in screen for the ECHO Unit Admin console.


Purpose
This is the dedicated authentication gate for the Administrator Web Portal. It restricts access to
authorised hospital administrators before any dashboard, staff, or room data can be viewed,
addressing the security and data-privacy requirements discussed in the Methodology chapter
(Section 3.10) of the proposal.


Key Functions & Interactions
    ●   Left panel: brand/marketing copy — "Oversee every echo room, technician and AI-predicted
        queue in one place" — communicating the scope of the admin console.
    ●   Admin ID field for entering the administrator's staff identifier (e.g., ECHO-ADM-014).
    ●   Password field (masked).
    ●   Two-factor access code field (a 6-digit authenticator code), implementing the two-factor
        authentication control referenced in the Settings screen and in Section 3.10 (ethical/security
        considerations).
    ●   "Sign in" call-to-action button that authenticates the administrator and routes to the
        Dashboard (Screen 2).
Correspondence to the Research Proposal
The proposal does not list a login screen among the eight named admin screens, but it is a
necessary precondition for all of them and directly implements the security/2FA requirement
discussed in Section 3.10 and configured on the Settings screen.


Notes / Corrections

  Observed discrepancy
  This screen is admin-only (it explicitly says "Sign in to ECHO Admin" and requires an Admin ID). It
  should not be confused with Screen 12, a separate, shared "Welcome back" login screen with
  Patient/Staff/Admin tabs found later in the same mockup strip. Two different sign-in designs
  exist in the file — only one (this one) is exclusively for administrators.
Screen 2: Today's Unit Overview (Dashboard)
 Primary Actor                    Administrator




       Admin dashboard — unit-wide KPIs, AI insight banner, room status, live queue, and system alerts.


Purpose
The administrator's landing page and 'control room' view. It gives unit-wide, real-time visibility of
technicians, patient throughput, echo room status, and anything that needs administrative
attention, directly answering the Chapter 1 problem of hospital management having 'no live visibility
of queue length, station status, or daily patient volume.'


Key Functions & Interactions
   ●    Left sidebar navigation grouped into Overview (Dashboard, Echo rooms), Management (Staff
        accounts, AI insights & reports, Audit log), and System (Settings), with the logged-in Super
        Admin's name and a Log out link pinned at the bottom.
   ●    KPI cards: active technicians, patients scanned today, echo rooms live, and AI prediction
        accuracy (e.g., 92%).
   ●    An AI insight banner (labelled with the ML model version, e.g. 'ECHO-ML v3.4.1') surfacing a
        natural-language recommendation such as staffing an extra technician for a predicted
        afternoon surge, with a 'View reasoning' link.
   ●    Echo Room Status panel listing each room, its assigned technician, and a live indicator.
    ●   A live queue snippet (queue number, wait time, status such as Live/Delayed, and a 'Manage'
        link into that room's queue).
    ●   System Alerts panel flagging issues needing admin attention, e.g. an SLA breach on the
        Stress Echo Suite, or technician accounts pending approval.


Correspondence to the Research Proposal
This is the 'Today's Unit Overview dashboard combining unit-wide KPI cards, station status, and
system alerts' described in Section 1.5 (Scope of the Study) as the first of the eight Administrator
Web Portal screens.

Notes / Corrections

  Observed discrepancy
  The proposal's scope section names only one staff modal ('Add-Staff-Member modal'). The
  mockups actually show two different staff dialogs: this detailed, tabbed Access & Role editor
  (used to review/edit an existing staff member such as Amara Silva) and a separate, shorter
  creation form (Screen 10). They should be read as two states of the same staff-management
  flow — edit vs. create — rather than two unrelated screens.

   ●   A chronological, timestamped timeline grouped by day ('Today'), each entry showing the
       actor, the action taken (e.g. 'approved a staff account', 'updated room hours', 'marked a
       patient scan done'), and the affected room/record.
   ●   Status-coloured icons distinguishing successful actions from security events such as a failed
       login attempt.

3. Summary of Corrections Made to the Original Framing
  ●   Not all twelve screens in the mockup strip are Administrator screens. Screen 12 ('Welcome
      back', with Patient/Staff/Admin tabs) is a shared, role-selecting login gateway used by all
      three portals, not an admin-only screen.
  ●   There are two different sign-in designs in the file: a dedicated Admin Sign-In (Screen 1,
      admin ID + password + 2FA code) and the shared, tabbed role-selector login (Screen 12).
      These should be documented as two separate screens, not duplicates of each other.
  ●   The proposal's Section 1.5 names a 'Register Station modal' and an 'Add Echo Room modal'
      as two separate screens, but the mockups only contain one room/station-creation modal
      (Screen 9), whose Room Type field already covers standard, stress, TEE, pediatric, and
      portable configurations. This should be reported as a single combined modal, not two
      distinct implemented screens.
  ●   The single 'Add-Staff-Member modal' named in the proposal is, in the mockups, actually
      three related but distinct dialogs: a formal creation form (Screen 10), a same-day quick-add
      shortcut (Screen 8), and a fuller Access & Role editor for existing staff (Screen 5). All three
      should be documented individually rather than collapsed into one screen.
  ●   Two supporting account screens — My Profile (11a) and Edit Profile (11b) — exist in the
      mockups but are not named among the eight core Administrator Web Portal screens in
      Section 1.5. They should be reported as additional screens rather than omitted or mis-
      mapped onto one of the eight.
